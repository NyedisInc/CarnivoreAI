when nothing in the guide fits

The rule: invent the SMALLEST extension of the existing language, then ADD it to this guide in the same change. A new style that is not written here does not exist for the next person, who will invent a different one.

  1. Prove nothing fits. Read the family's section and the canonical reference surfaces (references). Most "new" needs are an existing component with different content.
  2. Extend, do not invent. Change one property of the nearest existing pattern and keep the rest: same ground, hairline, corner, type, focus and accent rule. A variant (--compact, a new data state) beats a new component; a new component beats a new look.
  3. Check the rulings. If the extension changes or reverses anything recorded in docs/DECISIONS.md, CLAUDE.md or an issue thread, STOP and ask your own operator by name (Alex (example-owner) or Joe (ccsliinc)) before building ("RULINGS, BEFORE YOU REVERSE ONE").
  4. Build it to this guide's standard: tokens only, every state, every width, words first, every theme (making a component).
  5. Add it here, in the same change:
    • an entry in the fragment of the section it belongs to under client/style-guide/sections/: what it is, a live specimen or copied markup, when to use it and when not, how (classes, props, catalog keys), what it reads from the theme, accessibility, and the mistakes you already made with it;
    • its file and classes in client/style-guide/registry.json;
    • if it is a pattern other surfaces should copy, a line in do and do not;
    • a new section only when it truly is a new family: add it to registry.json's sections list and create its fragment.
  6. Record the ruling if Alex approved a new look: an entry in docs/DECISIONS.md with his words, the date and the issue.

The drift test (tests/test_style_guide_drift.py) enforces the registry half of this automatically. The fragment half is on you, and the next agent will build from whatever you wrote.
