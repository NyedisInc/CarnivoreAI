settings

Settings is a full-page menu page (settings redesign, 2026-09-28, docs/settings-and-pages-inventory.md) on the manager frame's chrome (web/src/lib/settings-page/SettingsScreen.svelte: .oc-page root (Page.svelte), .oc-titlebar title strip, no close button, Escape clears a search; each section and tab is its own #settings link), inside the page shell (the menu page shell), so it covers the screen behind it and the drawer's settings row is marked. It is compiled end to end: a section rail (with the search field on top) beside ONE tabbed page per section, a search over every setting, and a save footer inside the frame of every tab that holds a typed value. A section is a tab strip (page tabs, one tab per group, labels from the group labels) over the open group's rows; a section with one group draws no strip. Two sections, launch profiles and keyboard shortcuts, embed a whole screen (SettingsScreenSection.svelte, which calls provideInset() so that screen draws no second title bar). A deep link is #settings/<section>/<tab>. Every setting is ONE entry of web/src/lib/settings-page/settings-registry.ts and renders once.

account: the carnivore account
The first section of the rail (issue #1200): one carnivore-account row (carnivore_account) that draws the account body inline (web/src/lib/carnivore-account/AccountBody.svelte, the same body the #account menu page, AccountPage.svelte, puts on the manager frame). The page is the manager frame with sections separated by hairlines and a small tracked label each (acctpage__sec): identicon, handle (or "pick your handle"), email and "signed in with <provider>", the news email switch, the devices panel (SessionsPanel), the export and delete panel (AccountPanel) and sign out. Signed out it lists what the account unlocks and one sign in button that opens the sign in modal with source account_page. Strings are account.page.*. The Skills screen shows one line (screen__cta) instead of sign in panels while signed out.
anatomy
The rail (SettingsNav.svelte): .st-nav, the search field first (.st-nav__top), then one base ListRow per section, holding one whole-row Button (variant="row", data-section) with its icon (.st-nav__icon), label (.st-nav__label), the unsaved dot (.st-nav__dot, the page tabs' .oc-ptab__dot) and, while a search is typed, its match count (.st-nav__count, the button dimmed by data-empty at zero); an item carries no tooltip (no title; the section's hint shows as text in search results). The open section is the selected ListRow (aria-current="page" on its button). Below the sections, .st-nav__heading (an .oc-label, shown only while a plugin that is on has settings) titles one more row per such plugin, which opens the plugin's own settings form in the same frame. That form is the plugins page's own (.plp-region), drawn inside one Card titled with the plugin's name in PluginSettingsSection.svelte. Below 768px the list is gone and a native .st-nav__select sits beside the search field in one 44px row. The content column (.st-content) holds the tab strip (.st-tabs), then the open group's panel (.st-panel, with its one dim hint line .st-tabhint and its rows in .st-rows inside one Card, [data-st-frame]) or the embedded screen (.st-screen). The hosts list's .oc-page__items--list (now on the Pack page, .pk-screen) collapses the switch column on .mgr-card rows when no .mgr-card__head contains an .oc-check. The section's own title (h2.st-section__title) is visually hidden: the rail already says where you are.
a row
SettingRow.svelte on the generated settings form's row (.sf__row, .sf__label, .sf__hint, .sf__control, .sf__error): .st-row, its head (.st-row__head, .st-row__label), its help (.st-row__help) and its control (.st-row__control). The mark in the head (.st-mark) is a base Tag saying what happened to the last change: saving (neutral), saved (ok), unsaved (accent), not saved or invalid (danger). A search jump marks the row for a moment (.st-row--flash); a #settings/<section>/<tab>?highlight=<id> link marks the one control carrying data-highlight="<id>" the same way (.st-highlight-flash, settings-highlight.ts), waiting for it to render. A row whose feature needs a carnivore account while signed out is LOCKED (.st-row--locked): a dim label and, in the mark slot, a star in --oc-yellow-bright with a small "sign in" (.st-mark__lock, .st-mark__star); it stays usable.

an (i) note
web/src/lib/info-tip/InfoTip.svelte: a .info-tip holding a 16px .info-tip__btn (an italic i in a 1px hairline with a small square corner, muted, the accent on hover and while open) that toggles a one-sentence .info-tip__note (role="note") in place. a group is a tab
Alex (example-owner), 2026-10-03: every section is a tabbed page, so a group is one tab of the strip and only the open group's rows draw. The rows are ONE column in ONE base Card titled with the group's name ([data-st-frame], 880px at most, the card's one edge, a faint hairline between rows, the save footer in the card's foot), each a minmax(0,1fr) 280px grid: label and help left (.st-row__text), the control right (.st-row__control), vertically centred, so every control's right edge is one line (Alex (example-owner), 2026-10-03). Help is never under a control; a note such as a number's range is the muted .st-row__note under the help, and the unit sits inside the field (.st-unit, .st-unit__suffix, over a base NumberField). A setting with a registry parent is a child row (.st-row--child): 16px in behind a left hairline, and .st-row--off (dimmed, inert) while its parent makes it meaningless. Under 768px a row stacks. The shared .oc-group__main is not used here. A row alone in its tab is named by the tab and keeps its label for assistive tech only (.st-row__label--solo); in a section with no strip the row keeps its label. A panel-sized row spans the width (.oc-wide). The tabs and the rail item carry a dot while they hold a draft.

secret input
Every API key or token field (the settings secret control and the BYOAI connection key) uses the one secretField action (web/src/lib/secret-field.ts) and the .oc-secret class (web/src/opscenter/fields.css, on .oc-field): a plain type="text" input masked with -webkit-text-security: disc, with autocomplete="off", autocapitalize="off", spellcheck="false" and the password-manager ignore attributes data-1p-ignore, data-lpignore, data-bwignore and data-form-type="other". It is never type="password" (Chrome and Safari offer to save a password field, and Chrome remembers a field that was ever one), so no browser offers to store a key. Only a browser where CSS.supports('-webkit-text-security', 'disc') is false (Firefox before 114 and other old engines) falls back to type="password", since masking the key on screen matters more than the prompt there. Do not use it for the account's own login password: a password manager is right for that.

common mistakes

  • A setting drawn in two places. Joe (ccsliinc): "the settings are showing on multiple tabs." One registry entry, one section; settings-page.test.ts fails when a setting renders twice.
  • A typed value written on every keystroke. A half-typed shell path would be written and refused. Typed values wait for the footer save; choices apply at once.
  • A save button floating over the page or live with nothing to save. Save is the frame's footer and is dimmed until a draft waits (Joe: "save is not in a good place"; Alex, 2026-10-03: "save moves into the frame footer and the floating save bar goes").
  • Building a second place to edit something a feature's own page already edits. Wrappers are added and edited on the wrappers page; settings only keeps each family's legacy fallback command and links there.
  • A setting only this browser remembers. If other devices should follow it, it is a server preference; localStorage is for per-device conveniences only (the remembered section is one).
  • A config write around the one writer. Server config goes through src/core/config_writer.py only.
