# huddle: the interactive todo

The huddle is the owner's shared todo list. The owner reviews it by color and icon, not by reading the terminal. Use the carnivore MCP tools `task_manager_*` (load them with ToolSearch if deferred). They were `huddle_*` before rev 85: the old names still work for now; call the new ones (`huddle_focus` keeps its name). Every rule below is the standing way to work.

## 1. Reading
<!-- core -->
- A send that says "the interactive todo list ... changed" carries a list id and a since-cursor.
- Read it with `task_manager_changes` using those two values. Answer in the huddle, not in the terminal.
- The owner's changes (ticks, replies, adds, and his answers to your questions) are batched: one send goes out after a few quiet seconds (45 at most) and its since-cursor is the oldest change you have not read, so one read covers all of them. His answer reaches you in that same send, not at once.

## 2. Titles
<!-- core -->
- Every item has a short descriptive `title` (max 120 characters).
- If an owner-written item has no title, write one as soon as you see it.

## 3. Groups (every item is in one)
<!-- core -->
- EVERY item belongs to a group (the `group` field). No item is ever left ungrouped, including the ones you create: pass `group` on `task_manager_add`, or `task_manager_move` it right after.
- When you read a list, move any ungrouped item into the group that fits.
- If the owner put an item in the wrong group, or in none, move it with `task_manager_move`.
- If no group fits, create one (`task_manager_group_create`).
- Never make a group named after a status (no "Done", "Blocked", "In progress").

## 4. Guide revision
<!-- core -->
- These rules are the `task_manager_guide` tool's text; this skill is a copy of the same file.
- `task_manager_guide` is only needed before a write other than `task_manager_progress_set` and `task_manager_reply`. With no arguments it answers the core sections plus a one-line index of the rest; `topic: <number or name>` returns one section, `detail: true` returns the whole guide.
- Every huddle answer carries `guide_rev`; when it is higher than the one you last read, call `task_manager_guide` with `since_rev` set to that number. It answers `up_to_date` when nothing changed for agents, else a short summary of what did.

## 5. Reply kinds
<!-- core -->
- **info:** an fyi while you work. Use `task_manager_reply`. The owner sees each unread info in full on the row and marks each read on its own. An unread info keeps the task in his needs you (a read) until he marks it read or its status changes. An info never changes the status or ends working.
- **notify:** add `notify: true` to an info when the owner should know it is there: it marks the item unread and badges the huddle tab, and asks nothing. Use it sparingly. The old "look" (kind `attention`, or an `action` on a reply) is retired: use `task_manager_ask` for an answer, `task_manager_update` state `review` with `review_action` for a tick or push. An omitted kind is an info.
- **answer:** you are replying to a question the owner asked (in the huddle thread, or outside it). Use `task_manager_reply` with `kind: answer` and QUOTE the owner's question: `quote` is the id of the owner's message on that item (the server snapshots its text), or `quote_text` is the owner's words when they asked outside the huddle. The row shows ONE box, the owner's question muted on top and your answer below in markdown. It behaves like an info (never changes the status). Use `answer` when replying to the owner's question, `info` for an fyi they did not ask for. Form answers from the owner carry an `_extra` {text} entry in `answers` when the owner wrote something in the anything-else box: read it.
- **question:** you are blocked. Use `task_manager_ask`, never `task_manager_reply`. Ask it STRUCTURED: put any explanation in `context` (background, shown apart in a muted block) and the asks in `questions`, a list of short, precise questions (one per entry, no explanation inside) that the owner sees numbered and answers by number ("1 yes, 2 the second"). Use `text` only for a single plain question. The batch `ask` op takes the same fields.
- Keep every question short. When it needs explaining, post the explanation first as an info (or an answer, when replying to the owner's question), then ask the short question; prefer a typed form (section 32) over free text.
- Never put a question in an info.
- **Lead, then details:** start every info with a ONE-LINE LEAD (a short plain sentence, under about 100 characters), then a line break, then the details. The owner's row folds a long note (past about 240 characters or 3 lines) to that lead, with a chevron that opens the rest.

## 6. Working
<!-- core -->
- Set `state` to working with `task_manager_update` when you START. It is durable: it stays working across idle, restarts and dead sessions.
- It ends only when you post a question (`task_manager_ask`), set `review`, `waiting` or `open`, move it to `todo`, or the owner ticks or deletes it. An info does not end it, and neither does the owner's reply.
- Reading never makes an item working, sent or not. Only your own `working` does, so claim an item before you start it. Your claims end when you `/clear` or start a new conversation.
- Because it is durable, set `open` or `review` yourself when you stop an item.
- A `todo` item is wanted but not today: do not work on it unless the owner asks. Tasks are born `open`; set `todo` only when he explicitly asks to park that task (an add box entry whose text asks to park it counts), never for your own follow-ups; `open` takes it off. A project's own skill or CLAUDE.md may override this.
- A new task, and one he reopens (reply, untick), lands `open`: file it (section 3), then move it on. Every status change leaves a system line on the thread (`category: status`), not a post to answer.
- Any move of the item out of `open` (review, waiting, todo, done), by anyone, ends your claim, and so does a question. A task on the swarm lane cannot be claimed with `task_manager_update` `working`: work it through the swarm card tools.
- When the owner asks what's next or what's open, list working items first and resume them, then the open ones.

## 7. Review
<!-- core -->
- When the work is committed but not yet installed in the app the owner will review it in, set `state` to `waiting` (its own "waiting" section; use it for a reboot or a person you wait on too) WITH `waiting_on` and `wait_kind` (section 30); after the install, set `review` for review. Waiting on the owner is a question: use `task_manager_ask`.
- When finished, set `state` to `review`.
- Fill these in the same update. They show in the review block without opening the row. A review stays in the review section in the blue review color, never in "needs you", and its row shows no action tag:
  - `review_action`: what the owner must do. `tick` (check and tick), `push` (check and tick to push), `answer`, `read` (read only), `none` (no action needed). Unset reads as `tick`. Always set it.
  - `review_summary`: ONE plain line (about 140 characters, no markdown) saying what is done, shown above the folded description; set it when the description runs past a line or two. Absent: the description's first sentence.
  - `review_description`: what changed and what to check, in markdown (lists, bold, code, tables).
  - `review_link`: a clickable link, only when one helps (an in-app path or an https URL).
  - `review_where`: a short LOCATION ("Settings, Huddle tab"), only when useful; NOT a click path (no menu trail, version numbers or "reload").
  - `review_checks`: things the owner checks before closing; only he ticks. A new list replaces the old, `[]` clears.

## 8. Answers given outside the huddle
- When the owner answers in chat or in the terminal, call `task_manager_answered_set`.
- Also post an info reply recording the owner's decision, so the row's last line is not a stale question.
- `quiet: true` marks the owner's Comment (rev 103): context, never an instruction or sent to you.

## 9. Surfacing
- To get the owner's eyes on something, post an info with `notify: true` (it shows on the row in full, marks the item unread and badges the tab) and mark the task with a `marker` (section 17). That only informs him: for something you need from him, ask a question (`task_manager_ask`, a typed question works from the collapsed row) or hand the work over for review (`task_manager_update` with state `review`).
- A question moves an item into the "needs you" section. So does an unread info, as a read, until he marks it read or the status changes. A review never does.
- In normal density, pass `open: null`. The row shows the reply box, so it does not need opening.
- The owner reviews by color and icon in the huddle, not in the terminal.

## 10. Approval
- A tick (approved) is the owner's alone. Never tick for the owner. `task_manager_update` cannot touch an approved item; to reopen one (or close one), see section 26.
- `review_action: push` asks the owner to check the work and tick to approve a push. Never push on your own; follow the project's own rules for what a tick authorizes.
- A write that waits for the owner's approval answers pending with an `act_...` id: call `approval_wait` with it. Approvals are not shown in the huddle (guide rev 22): no huddle item, post or send carries them, so read the outcome with `approval_wait`. Nothing expires. Do not pass `huddle_item` on those tools; it is ignored.

## 11. Batching and lean answers
- Two or more edits (adds, state changes, replies, moves) in one go: send ONE `task_manager_batch_run` call (`list_id`, `ops`, at most 50), not one tool call each. An `add` op takes the `task_manager_add` fields (no item_id) and its own optional `list` (default `list_id`), so one call files items across projects. It answers per op `{item_id, ok, state, revision}` and is not atomic: read the `ok` flags, the earlier ops stay applied.
- Single writes (`task_manager_add`, `task_manager_update`, `task_manager_reply`, `task_manager_ask`, `task_manager_move`, `task_manager_answered_set`) answer lean BY DEFAULT: `{item_id, ok, state, revision}` (plus `message_id`). Pass `lean: false` only when you need the full item and its thread back.
- `task_manager_tasks_list` is a LEAN read by default: one summary row per open item (`id`, `number`, `title` (or the first 120 characters of the text), `status`, `section`, `unread`, plus `group`, `needs_action`, `forked_from`, `review_action` when set), no threads, no approved items (the answer says `approved_hidden`). Opt in with `fields` (a list of `text`, `note`, `thread`, `review`, `state`, `kind`, `revision`, ..., or `full` for the whole item), `include_approved: true`, `item: <id>` (ONE item in full with its thread: use it before you edit or reply on an item whose text you need), `limit` (default 100) and `cursor` (the previous answer's `next_cursor`; it is a paging offset, not the change cursor). Reading the list still counts as reading the approved items it hides.
- `task_manager_changes` is lean too: groups come only when they changed since your cursor (or on a reset); an item whose revision and group you already hold (from a list read of any shape, or an earlier changes) arrives as `{id, status, section, revision}` whatever moved it (a new message, a bulk renumber); read an item's text with `task_manager_tasks_list item`. Your OWN posts are left out of `messages` (`omitted_own` counts them; `include_mine: true` keeps them); the owner's posts always come whole. A form question or answer message sends its `form` / `answers` structure plus only a one-line `text` lead.
- `task_manager_schedules_list` lists every scheduled item across all lists (`list` omitted or `all` means every list; soonest next fire first; `list` and `paused` filter it): read it before you schedule or pause something, to see what already fires and where.
- `huddle_focus` (deprecated and switched off by default; use `marker`) with `list: "all"` accepts items from any project's list.

- There is no delete tool, and a `delete` op in `task_manager_batch_run` is refused for agents: only the owner deletes, and a delete is for good. To ask, see section 27.

## 12. Names
<!-- core -->
- The owner reads titles. When you mention an item in a reply, review field or chat message, name it by its title in quotes. Ids are for tool calls only.

## 13. Formatting and data
Your posts (task_manager_reply, the context of task_manager_ask) render a safe markdown subset: **bold**, *italic*, `code`, fenced code, `-` and `1.` lists (one nested level), `#` and `##` headings (drawn small), `[text](https://...)` links (http and https only), pipe tables and a key: value block. HTML shows as literal text. A fenced code block draws as a command area with a copy button, so put anything the owner should run or paste in a fence. Use the form that fits: a pipe table to compare things or list rows of data (numeric columns right-align on their own), a ```kv fence of `key: value` lines for a few labeled facts (branch, status, count), a short list for steps or options, prose otherwise. Keep the one-line lead first, then the details. An item's own text (task_manager_add, task_manager_update) stays plain.

## 14. Tool reference (moved out of the tool descriptions, which stay under 400 characters)
- **Statuses and sections** (an item's `status` and `section`; its `state` decides the section, an info never moves it): `question` (your question waits on the owner), `review` (you marked it done), `waiting`, `working`, `waiting_to_send` (the owner changed it and neither a send nor your read has carried it yet; only a read by the list's own session, the session its send went to or is held for ends it), `scheduled`, `open`, `todo`, `done` (approved). Numbers are the owner's view order; a checked item's number is null.
- **Working is durable** (see section 6): a read never makes an item working, with or without a send; only your `task_manager_update state: working` does.
- **Groups are areas** (widgets, mcp tools), never states. Each list answers its named groups (`id`, `name`, `position`); an item's `group` is null when ungrouped.
- **Messages**: each thread message has a `kind`: `question`, `info` (yours), `attention` (an old look, still shown in old threads; you cannot post one now), `reply` (the owner's). An unread info the owner has not read carries `unread: true` and the item `info_unread`. A message the owner attached files to carries `files: [{name, mime, size, path}]`; every `path` is ABSOLUTE and local, so Read it (an image or a document) to see what the owner sent.
- **Typed questions**: see section 32.
- **Scheduling** (`task_manager_add` / `task_manager_update`): `fire_at` (ISO 8601 WITH a UTC offset, in the future; empty cancels) sends the task's OWN session (the one it is tagged to) its prompt when it comes due, woken if asleep; only when that session is gone does it go to the project's lead, then the list's default, waking or starting the project's session first; approving or deleting the item cancels it and a todo item does not fire. An open item with a pending `fire_at` has status `scheduled` until it fires; a failed fire shows its error and leaves it open. `repeat` ({freq: daily, time: 'HH:MM'}, {freq: weekly, byweekday: [0-6, Monday is 0], time}, {freq: hourly, interval: N}, {freq: monthly, monthday: 1-31, time}; times are 24-hour in the app's configured time zone and DST-safe; empty string stops) re-arms after each fire; a missed occurrence while the app was down fires once. `paused` pauses or resumes a repeat; `fire_now: true` runs the item now through the same delivery (refused for an approved or todo item). `start_trigger` on an item shows all of it.
- **Forking**: `task_manager_fork` makes a new item beside one (title and text copied unless given); `fork_state` sets the fork, `parent_state` the original, in one transaction (never an approved state); the fork records `forked_from`. A fork is a subtask: `task_manager_tasks_list item` of the parent lists them under `forks`. `parent_waits: true` makes the original wait on its forks (section 31).
- **Moving**: `task_manager_move` sends an item to the bottom of another list (project ids from `projects_list`; `all` is the shared list) and/or into a group (an id or area name; a new name makes it; null ungroups). Numbering recomputes in both lists.
- **Stale writes**: `expected_revision` on `task_manager_update` refuses the write if the item changed since you read it.
- **Plain text vs markdown**: an item's own `text` is plain; formatted detail goes in a `task_manager_reply` post. `task_manager_batch_run` ops take that op's own tool fields (`add`, `update`, `reply`, `ask`, `move`, `mark_answered`, `delete`, `fork`); `list_id` is the list every item must be in (`all`, a project id, or `mine`); at most 50 ops; `stop_on_error: true` skips the rest after the first failure.

## 15. Live worker state (`task_manager_progress_set`)
<!-- core -->
- The owner cannot see what your workers are doing, so tell the huddle, not the terminal. When you start work on an item, set `task_manager_update state: working`, then call `task_manager_progress_set {item, phase, note?, worker?}` at each change: `queued`, `running`, `testing`, `installing`, `blocked` (say what you wait on in `note`), `done`. The row shows one line per worker (a phase chip, your note, the elapsed time).
- `worker` is your label ("orchestrator", "web", "api"). Each label keeps ONE line, replaced by its next call; up to 8 labels per item. Omit it for a single worker (label `main`).
- Keep `note` short, about 60 characters ("34 of 120 tests", "installing build 42"). It is a status line, not a report: results and questions still go to `task_manager_reply` and `task_manager_ask`.
- In a batch, use the op `progress` with `item_id`, `phase`, `note`, `worker`.
- A line with no update for 30 minutes shows dim as stale, and a line older than 6 hours is dropped. The lines live in memory only: re-send your current phase after an app restart.
- Do not spam it: one call per real change of phase or milestone.

## 16. Extending the huddle rules (personal add-on skills)
- An owner may keep personal additions to these rules in a skill of their own (for example `huddle-joe`). Where the two differ, the add-on wins.
- The add-on declares the rules revision it was written against in its front matter: `extends: huddle` and `guide_rev: <the guide_rev you checked it against>`.
- When the app's `guide_rev` rises above an add-on's, the Skills page marks it "behind the huddle rules (written for rev N, now M)" with the changes since N, and every huddle answer carries `stale_extensions: [{name, written_for, current}]` (present only when something is behind).
- When you see `stale_extensions`: read the changes (`task_manager_guide` with `since_rev` set to the add-on's `written_for`), check the add-on for anything that now conflicts or is redundant, fix it, and only then raise its `guide_rev` to the current one. Never raise it without checking.
## 17. Markers (guide rev 96, replaces the flag colors of rev 4)
- A marker marks one task for the owner with ONE solid shape in its own color, so he can find it again. Shapes: diamond, square, triangle, circle, hexagon, pentagon, star, cross. At most one per task, last write wins.
- Set it with `marker` on `task_manager_update`, `task_manager_reply` (the task is marked after the post) or a `task_manager_batch_run` update or reply op. `marker: ""` clears it. An unknown name is refused with an error that lists the shapes. A marker never stands in for a status.
- The marker lives on the task, not the message. It clears by itself when the owner approves the task or it is deleted; an approved task takes no marker.
- The owner sees the shape in the row's left margin, and a filter in the list bar that lists only the shapes in use; picking shapes shows just those tasks with every project and section open. Reads (`task_manager_tasks_list`, `task_manager_changes`) carry `marker` only on a marked task.
- Deprecated, still accepted for now: `flag_color` reads as a marker (purple is star, pink is cross, teal is hexagon, lime is circle) and `flag_reason` is ignored. `huddle_focus` is deprecated and switched off by default: mark the task instead.

## 18. Cards (guide rev 6)
- A task item is a card, shown in four columns worked out from its state: Todo (open, nobody holds it), In Progress (open and held, or a plain session is working it), Review (you marked it done, or a Swarm agent finished it) and Done (approved). Nothing is copied: the column is a view over the item.
- **Swarm agents drive cards only with the `swarm_card_*` tools** (`swarm_card_start`, `swarm_card_handoff`, `swarm_card_finish`, `swarm_card_release`, and for a project agent `swarm_card_list`, `swarm_card_deal`, `swarm_card_create`, `swarm_card_reorder`). A Swarm agent keeps its handoff current, finishes with a result and short how-to-validate steps and `needs_owner` (false: checked, complete work goes straight to Done; true with `owner_ask`: Review, waiting on the owner's answer, pick or hands), and a project agent closes its own project's Review cards with `swarm_card_close` (#2600).
- **Plain sessions keep the huddle tools and their claim** (`task_manager_update state: working`), which never lapses and is never dealt or handed off. You are a Swarm agent only when the Swarm spawned you (your brief says so); every other session is a plain session and works exactly as sections 1 to 17 say, with no card needed.
- **`task_manager_update` of its state and `task_manager_move` on a Swarm-held card are refused** with "card is held by a swarm agent": the holder moves it with the card tools, or the owner releases it. Ask the owner or the project's agent instead of forcing it.
- **Only the owner, or the project's auto-done switch, reaches Done.** A finished card waits in Review for the owner's click; a send-back note from the owner returns it to work and becomes a project fact.
- The full design: `docs/swarm-cards.md`.

## 19. What reaches the owner (guide rev 13)
- **Only an actionable post gets the owner's attention**: a question (`task_manager_ask`), or a review (`task_manager_update state: review`, or the review fields). An info, an answer, a move and a plain edit ask nothing: an unread info puts the task in needs you as a read (until he marks it read or the status changes), but on an open or working item he keeps folded it is easy to miss.
- **A question never goes in an info.** `task_manager_reply` of kind info or answer is refused when the last non-empty line ends in `?`, or when two or more numbered lines end in `?` (an omitted kind is an info). The refusal reads: "questions go in task_manager_ask with `questions`; an info is never answered". Move the question to `task_manager_ask` with `questions`.
- **A plain `task_manager_ask` text with two or more `?` and no `questions` is refused**: pass the questions as `questions`, one entry each, so each is answered on its own.
- **Override**: `not_a_question: true` on a `task_manager_reply` (or a batch reply op) when the text only ends in a question mark and asks the owner nothing. Use it rarely.
- **Every write answer carries `reaches_owner` (bool) and `reaches_owner_reason` (short text)**, also in lean answers and in each `task_manager_batch_run` result. Read them: `false` on something you needed him to see means you posted the wrong kind.

## 20. Your own project's list (guide rev 14)
- **Write to your own project's list** (`list: mine`). Every huddle write is checked against the project of the session making it: a write that lands on another project's list (a `list` argument, or an item, group or move target that lives there) is refused with a plain warning naming both projects.
- **Another project's list needs `cross_project: true`** on that call (or on that op of a `task_manager_batch_run`), and only when the work really belongs there. The answer then carries `cross_project: {from, to}`, the item gets a "written from another project" line on its thread, and the owner sees it as cross-project.
- **A refused batch op fails alone** (`ok: false` with the warning); the other ops run as usual.
- **Not checked**: reads, and a session that belongs to no project (the answer carries `warning: "could not tell your project"`).

## 21. Nudges (guide rev 20)

The nudge plugin, when the owner turns it on, covers every project unless the owner switched that project off, and a single session can opt in or out. Every nudge send starts `huddle nudge:` and names ONE item or a few of yours; answer it on the item, never only in the terminal.

- **A claimed item gone quiet** (`huddle nudge: no progress for N min on "..."`): post `task_manager_progress_set` and keep going, set `review` or `waiting` when it is done, ask with `task_manager_ask` when you are blocked, or set `open` when you stopped.
- **An open item nobody claimed** (`huddle nudge: "..." has sat open and unclaimed for N min`): if you are free, claim it with `task_manager_update` state `working` and keep going; ask with `task_manager_ask` if blocked; leave it open if you cannot take it.
- **You are idle with no claimed item** (`huddle nudge: you have been idle for N min and hold no swarm item. Pick up the next open item, "..."`): claim that item the same way, or ask.

It is only ever sent to an idle session, one item per nudge, never for an item that waits on the owner, on the back burner or `waiting`, or that carries a pending one-time `fire_at` or an armed repeat in ANY state (working included) (there is no install nudge). An open task counts as stalled only when the session that owns it (its claimant, else the session that last held it, else the project lead) sits idle past the timeout with the task still open; a reply of the owner's that nobody picks up stalls the same way. A task whose owning session has died is never nudged: once it has sat quiet for the timeout, Carnivore wakes that session if it is only asleep, else the project lead takes the task, and with no lead Carnivore raises ONE question to the owner (do not answer it). After several nudges with no change Carnivore itself raises ONE question on the task with three options, unstick, park and cancel. It is the owner's: do not answer it. Park moves the task to `todo`; unstick and cancel leave it `open` and the choice rides your next send, so read it and decide (a cancel means you decide what happens next). It raises no toast and no phone alert.

## 22. Filing inbox entries (guide rev 25)

The owner's add box no longer creates an item. It queues his raw text as ONE inbox entry (a whole multi-line paste stays one entry) and sends it to the project's lead, else its most recently active session: `huddle inbox: ... file entry N with task_manager_entry_import ... Raw text: "..."`. You file it. If nobody does within about two minutes (a setting) the entry stays queued and the server asks the owner what to do (file it himself, start a session, or wait), so do it promptly, and never create the items yourself with `task_manager_add`.

- **Call `task_manager_entry_import`** with `inbox_id` and `items`: one or more `{title, text, group?, state?, ask?, perceived_ask?}`. Give each item its `perceived_ask`: one plain line of what you understood the owner to want. `task_manager_entries_list` shows entries still waiting, with the full raw text. The send may have flattened line breaks into " / ".
- **Split the request.** One item per separate thing he asked for ("fix the login bug and add dark mode" is two items). Keep one item when it is a single task with steps. Never split a sentence into fragments, and never merge unrelated asks.
- **Leading directions steer it.** The words at the start of the text (or of one request inside it) are instructions to you, not part of the item. Drop them from `text`:
  - `backlog x` (also `back burner x`, `later x`): state `todo`, because the leading word is his explicit ask to park it. You do not work it. The ask need not be a leading keyword: his own text saying "park this", "for later" or "not now" about a request also files that item `todo`. When his text does not ask to park it, the item is born `open`.
  - `now x` (also `do x now`, `start x`): state `working`. You file it and start it, as with `task_manager_update state: working`.
  - `ask x` (also `question x`): state `question`; the item's text is the question, or pass `ask: {context, questions}` for typed questions.
  - nothing leading: state `open`.
  - A direction may apply to one request inside the entry ("backlog dark mode, now fix login" files two items with two states).
- **Title and group every item** as in sections 2 and 3: a short title, filed into the area group it belongs to (`group` is an id or an area name).
- **The original is kept for you.** The raw text stays on the entry and every item you file shows it as "from the add box"; do not copy it into the item. If it is ambiguous, file your best reading and say so in an info reply on the item rather than asking.
- A late call (the entry already fell back or was filed) is refused with how it ended; do not retry.

## 23. Artifacts: show a page (guide rev 26)

When the owner should SEE something, not read about it (a visual, a preview, a mock-up, a before/after, a comparison, a chart or diagram), post it with `task_manager_artifact_add {item, title, description, html or file_path}`. The thread shows a card (title, description, open); open shows your page in a locked-down frame, and the owner can pop it out into its own window.

- **One self-contained HTML document, up to 2 MB.** Inline all CSS and JS; embed images and fonts as `data:` URIs. Nothing external loads: no network, no CDN, no fonts from the web, no `fetch`, no links out, no cookies or storage, and the page cannot talk back to the app.
- **Prefer text for text.** An artifact is for what a paragraph cannot show. Give a plain `title` and a one-line `description` saying what to look at.
- **A question goes beside it, not inside it.** To get an answer, follow the artifact with `task_manager_ask` on the same item; it sits right under the card. The page has no buttons that reach you.
- It marks the item unread (like an info with `notify`). Use `file_path` (absolute, `.html`, not a symlink) for a page you wrote to disk; pass exactly one of `html` or `file_path`.

## 24. Your items on every answer (guide rev 30)

Every huddle answer can carry `your_items` (up to 5 of `{id, title, state, age_min}`) and `your_items_more`: the items you hold in `working` (your claim) or `waiting` (on your project's list). It is what you still owe: finish it, install it, look at it on the live page, then set `review` with a review or `task_manager_ask` if blocked. The field is absent when you hold nothing.


## 25. The session that holds an item working owns its sends (guide rev 34)

- When you set an item `working`, your session owns that item's sends. The owner's later changes to that item (a reply, a tick, an answer, an edit) are sent to YOU, even when another session last used the huddle on that list. Such a send names the item ids: `... changed (item ids 12, 15): read it with ... (list 18, since 40)`. Read that list from that cursor as always.
- You keep the item after `review`, `waiting`, a question, `open` or `todo`, so the owner's reply on your review reaches you. The owner's tick ends it once the tick has been sent (the tick is sent to you, even if you never tagged the item); a delete ends it at once; another session's explicit `working` takes it over. Reading an item never takes it over.
- `task_manager_tasks_list` rows carry `owned_by`: the label of the session that holds the item's sends, while that session is live. When it is gone (archived or deleted, measured, never guessed), the project lead takes the item; with no lead Carnivore asks the owner, and meanwhile the item's sends go to the list's usual session.

## 26. Reopening or closing an item the owner settled (guide rev 42)

- An approved item is the owner's: `task_manager_update` refuses it; ask with `task_manager_state_request` `{item, action, reason, to_state?}`.
- `reopen` takes an approved item back to `open` (or `waiting` via `to_state`); `close` ends an open one approved (his approve is his tick).
- `undo_completion` asks him to undo a closure. A `correction` message (`retracts`) means he undid one or cancelled the task: stop (delivery proves nothing). A late result on a cancelled task lands unread and it stays cancelled.
- Every request waits in his approvals inbox. The card shows the title, current and target state and your `reason` (500 characters at most); nothing changes until he approves. The answer is `pending` with an `act_...` id: read the outcome with `approval_wait`; it is also a thread line (applied, not applied because the item changed, or denied).
- Asking again about the same item while a request is pending updates that one card (new reason); it never adds a second. Ask once with a real reason; do not retry a denial.
- A reopen of an item that is not approved, or a close of one that is, is refused before any card is filed: change those yourself with `task_manager_update`.

## 27. Movement rules (guide rev 57 to 61, 64)

- **Born open or todo.** `task_manager_add` takes `state`: `open` (default: you are sent it and decide when to work it) or `todo` (parked until the owner releases it; only when he explicitly asked to park that task, a project's own skill or CLAUDE.md may override this default). Tasks are born open. Any move after that is its own step in the item's history.
- **The blocker check.** Every move you make passes it. A task waiting on its forks (section 31) stays in `waiting` whatever state you ask for (`todo` excepted); the answer carries `blocked` saying why, and the history records the stop. A park ends when you move the task out of `waiting` (that is you clearing it). The owner's own moves are never blocked, except his tick (section 33). Park an item (`state` todo) only when the owner explicitly asked to park it (no approval step, but never for your own follow-ups).
- **One open question per item.** A new `task_manager_ask` folds the older open question on that item, marked superseded. The owner's answer, a submit or a cancel sends the item to `open`; you decide the next state.
- **The owner's reply on a review or a done item opens it.** The item is `open` the moment he replies, and its history says "joe replied", so he never sees a task sit in review with his question unanswered. `task_manager_changes` lists such items in `owner_replied` until you answer. If he asked a question, answer it with `task_manager_reply`, then return the item with `task_manager_update` `state: review`; a task he had ticked returns to `done` with `state: done`, allowed only while it is open because of his reply and after you posted your answer (it is a restore recorded under your session, never his tick, and you can never tick or reopen it otherwise). If he asked for changes, leave it `open`, work them, and set `review` when finished. `task_manager_reply` `changes` is accepted and does nothing.
- **An info after his unanswered message is an answer (rev 93).** His newest message on an item is unanswered until you post an `answer` or a question after it, or set `review` after it; a form submit and a review board round need no answer; Carnivore's questions never answer him. While it is unanswered, an info you post (an omitted kind, `info`, or `attention`) is stored as an `answer` quoting it, `notify` dropped (an answer never marks the item unread), and the result carries `stored_as_answer_to` (his message id) and an `owner_guard` note, in lean and batch answers too. `not_a_question` does not change it. A reply with `file_paths` stays an info and the note says to answer in a separate reply. A `cross_project` reply is never changed. Send `kind: answer` with `quote` yourself.
- **Review means ready to be closed, never still working (rev 93).** Your `review` (also `done_by_claude`, a batch `update`, a fork's `parent_state` or `fork_state`) is refused, naming every reason, while: his newest message is unanswered, your own question on the item is open, a subtask of it is not in `review` or `done` (section 33; a fork's `parent_state: review` counts the new fork), or the item text, review fields or thread names a queued handoff (`~/.handoff/pending/<name>.sh`) with no `~/.handoff/log/<name>.result`. On an item in review, your question, fork or queued-handoff message reopens it. `task_manager_answered_set` is only for his terminal answer. The owner's moves are never refused; only his tick waits on subtasks and blockers (section 33).
- **Unticking goes to `open`**, always. Ticking a task that repeats clears its review and returns it to scheduled with the repeat intact; only a one-time task goes to done. A one-time schedule that comes due while the item is `waiting` is delivered to the item's CURRENT session like any other; one that comes due while the item is on the owner's turn or on the back burner is skipped, the reason is written on the row and as one info line on the item's thread, and it fires at the next pass once the item leaves that state. Any `fire_at` may sit on a `waiting` item whatever its `expect_by`: the wake-up is delivered either way. Repeats are not refused. A delivered fire leaves one info line on the item's thread naming the session it went to (saying when that was the list's lead, and why when the task's own session was gone), so check it to see whether it woke you; a repeat posts it only when its target changes.
- **Delete is the owner's.** Ask with `task_manager_state_request` `action: delete`, the item and a reason. The card waits in his approvals inbox (never auto-approved) and his approve removes the item, its thread, history and files for good. Remove completed only hides: history stays.

## 28. Review boards: show a mockup in rounds (guide rev 63, 68, 69, 89, 90, 91, 96)

When a mockup needs several rounds of the owner's review (ticks, checks, notes on the page itself), use a review board instead of `task_manager_artifact_add`. It needs the review board plugin on and its boards folder set; if a call is refused with `reviewboard_no_root` or `cplug_disabled`, say so and fall back to `task_manager_artifact_add`.

- **`task_manager_board_create {name, title, task, summary, html or file_path, viewport, prompts, anchors}`** starts a board for the huddle item `task` and posts revision r1. **`task_manager_board_revision_add {board, summary, html or file_path, answers_round, prompts}`** adds the next one. `task_manager_boards_list` and `task_manager_board_get {board, since_round}` read them. **`task_manager_board_focus {board, revision?}`** puts the board on his screen (a row in his browser list, shown in the center screen); use it to point him at a revision you just posted. Revisions never change; a typo fix is a new revision.
- **Ask with `prompts`, not in the page.** A prompt is a `choice` (one option), `multi`, `check` (one box) or `question` (his words). The owner answers in a tray beside the page; the page itself can only point. Tag the parts he may point at with `data-rb-anchor="<id>"` and list them in `anchors`. State `viewport` truthfully (a sidebar 300, a pop-out 520, a page 1400).
- **Or ask a list of questions with a `layer`, no page needed.** Pass `layer: {kind: "questions", v: 1, title, items: [...]}` instead of `prompts` and leave out `html`: the board draws the questions inside its frame. An item is `{id, kind, label}` with kind `yesno`, `choice` (pick one, `options`), `multi` (`options`, `max` is enforced, `min` only shows as unanswered), `toggle`, `text` or `longtext`, plus optional `help`, `group`, `required`, `default` and `anchor`. An `anchor` (declared in `anchors`) draws the question right under that part of your page if you also pass `html` with `data-rb-anchor` parts; `placement: "float"` puts every question in one panel at the frame's edge instead. Each question has a note key. His answer comes back (`revision.draft`, a round's `payload`) as `{layer, v, values: {item id: value}, notes: {item id: text}}`; an unanswered item has no key, so absent means unanswered, never zero. A layer revision carries no `prompts`. `layer: {kind: "canvas"}` is the same as `payload_mode: true`.
- **Or review a list of rows with a `rows` layer.** Pass `layer: {kind: "rows", v: 1, title, choices: [{id, label, tone}], rows: [...]}` with no `html`: the board draws each row with its own picks and a note, like a review page of findings. A row is `{id, title}` plus optional `tag` (a small chip), `lines` (up to 8 `{label, text}` plain-text lines such as you had / now / my take), `meta` (a footnote such as a sha), `group` (consecutive rows sharing it get one heading), `anchor`, `choices` (this row's own picks, replacing the layer's), `suggest` (a choice id marked as your take, never picked for him) and `default` (a pick you carry over from his last round; the board carries nothing itself). `choices` take a `tone` of `ok`, `push`, `later` or `none`, which only colors them. `pick: "several"` lets a row take a list of picks (default one). His answer comes back as `{layer: "rows", v: 1, values: {row id: choice id, or a list of ids when pick is several}, notes: {row id: text}}`; a row he did not pick has no key. At most 200 rows and 12 choices.
- **A canvas page can ask for a max width.** Pass `max_width` (integer CSS px, 480 to 2400) on a page revision (not a layer) and the board holds that page to that width, centered, with a key in the board bar that switches between it and full width (Joe's choice is remembered on his device). Leave it out and the page is full width with no key. It applies to that revision only, so repeat it on each revision that wants it. Questions and rows layers have their own fixed width and ignore it.
- **His send is his reply on the task.** It is the same reply he types in the thread, so it follows the usual reply rules. His reply text lists his picks, checks and notes and ends with a `read it: task_manager_board_get ...` line; `since_round` is the number of the round BEFORE the one you want, so `since_round: 1` returns round 2. Read his rounds with `task_manager_board_get {board, since_round}` (his words word for word), then make the next revision and name the round it answers with `answers_round`.
- **A revision posts a card on the task and, by default, puts the task in review** (`request_review: false` posts only the card). Another project's task needs `cross_project: true`, like every huddle write. Never hand-edit a board's files; the tools are the only writer.
- **Run it live when the owner wants to watch you work.** `task_manager_board_live_set {board, summary, html or file_path, prompts?, anchors?, inline_picks?}` OVERWRITES the board's one working draft: no new revision, no card, and the task's state stays put. Leave `board` out and pass `name, title, task, viewport` to create a board that starts live. He sees the page follow each overwrite. When he (or you, on his word) says "bookmark that", call `task_manager_board_milestone_add {board, name}`: it freezes the draft as a named revision and asks for review; only milestones are kept. `task_manager_board_live_stop {board, milestone?}` ends the session (name a milestone to keep the draft first) and hands the task to review. His sends on a live board reach YOU directly as a message in your session, not as a reply that moves the task. Scratch boards and layer or payload pages cannot go live.
- **`inline_picks: true` draws each prompt right under its `anchor` row** on the page, in the trusted tray layer; tag block-level parts (a heading, a paragraph, a table row, a list item) with `data-rb-anchor` and name them in `anchors`. Dragging or editing on the page is not supported.

## 29. Roles: the project lead, do not disturb and tagged agents (guide rev 65 to 67, lead changes rev 78, 79, 81 and 84, do-not-disturb claims rev 98)

- **The project lead** is the project's Swarm project agent when it has one (a session the owner or the retrofit promoted keeps its conversation); a project without one has one ordinary session as its lead. Unclaimed tasks are its: the owner's send goes to it ahead of the project's usual session (the owner's own pick of a session always wins). There is no automatic successor: when the seat is empty, the owner picks a lead from the session menu, or you take it with `task_manager_role_set` `{role: lead, on: true}`, which works only while it is vacant. If someone leads already you are refused with their name: ask the owner. `{role: lead, on: false}` gives it up.
- **Do not disturb**: `task_manager_role_set` `{role: dnd, on: true}` on yourself stops NEW tasks reaching you by default. Your own claimed tasks, crosstalk and a session the owner picks himself still reach you. A lead cannot go on do not disturb (it is refused), and taking the lead seat switches it off.
- **Do not disturb also means do not grab** (rev 98). On do not disturb, a write on a task NOT assigned to you is refused with `dnd_not_assigned`: `task_manager_update` (working, tag, text, anything), `task_manager_reply`, `task_manager_artifact_add`, `task_manager_progress_set` and `task_manager_fork`, also as batch ops. Assigned means tagged to you, created by you, or held working by you right now. Do not take the task. Ask the owner with `task_manager_ask` on that task (asking is never refused); his answer on the thread, or his tagging it to you, lets you proceed. If you must act now, repeat the call with `reason` (at least 15 characters, why this task is yours): it goes through and the reason is posted on the task as an info the owner is notified of. Tasks tagged to you keep working as before.
- An asleep lead is woken when work reaches it. If the lead is archived or deleted the seat moves up to the company agent, else SysOp, and the owner is asked to pick a new lead.
- `task_manager_lead_set`, `task_manager_leads_list` (read only) and `task_manager_leads_update` change who leads: the first and last wait for the owner's approval. Setting the lead of a project that has a project agent re-points the agent to that session. A project whose folder sits inside another project's folder (Fleet Docker inside Fleet) may be led by the project agent of the nearest enclosing project that has one; no other project's agent can lead it. A project that is a company's HQ folder is led by the COMPANY agent: `task_manager_lead_set` with `agent` true (and `task_manager_leads_update`, whose plan row is `promote_company`) promotes the session into the company agent, keeping its conversation.
- **A pinned seat** (rev 84). `task_manager_lead_set` with `seat_only` true puts a live or asleep session of the project in the Task Manager lead seat and leaves the Swarm project agent alone (the owner's own main session, with full tools, beside the read-only agent). That session is the lead for everything the Task Manager routes (sends, tagged tasks, a gone owner's tasks, nudges) while it stands; the Swarm still routes its own work to its agent. `task_manager_leads_list` reports such a project as `pinned_seat` and never promotes it. `seat_only` with `session` null releases the pin; a plain `task_manager_lead_set` re-points the agent and the seat goes with it.
- You can read your own roles: `task_manager_tasks_list` on a project list carries `roles: {lead, you: {lead, dnd}}`, and `sessions_list` shows `task_lead` and `do_not_disturb`. Only the owner changes another session's role.
- **A tagged task** belongs to ONE agent's round trip: `task_manager_update` `{item, tag: "me"}` tags your own session, `tag: "<id from agents_lookup>"` tags another agent on this computer (a session with its own pane, never a subagent; a session on do not disturb cannot be tagged by someone else), `tag: ""` clears it. It is also an update op in `task_manager_batch_run`. A task you add yourself (`task_manager_add`, the batch `add` op, inbox filing) is tagged to your own session automatically, so the owner's tick and replies come back to you; an external token's adds are not tagged, and `tag: ""` clears it. The owner's send goes to the tagged agent first, waking it if it is asleep, as an ordinary send (the usual `task_manager_changes` line, not a crosstalk message). The tag stays through the owner's tick. If the tagged agent is gone, the project lead takes the task; with no lead, Carnivore asks the owner (unstick, park or cancel; it is his to answer, do not answer it). The same holds for the session that owns or claimed any task: when it is archived or deleted, the lead takes the task (the thread's lineage says `session_gone`), else the owner is asked. Items carry `tagged_session_key` and, while the agent is live, `tagged_by`.
- When the owner answers a stall question with `unstick`, Carnivore sends ONE send to the session that owns the task, waking it if asleep: read it with `task_manager_changes` and decide. When the owner answers `unstick` on a "tagged agent is gone" question, Carnivore wakes (or starts) the project's session, RE-TAGS the task to it once it is measured live, and sends to it, so later scheduled fires go there; when no session takes the task the tag stays cleared and one info line on the item says the task has no session now.

## 30. Offer a schedule, and read the thread a send names (guide rev 72)

- **`task_manager_reply` takes `offer_schedule: {when, title}`** when your reply proposes a follow-up for a later time (for example, "keeping the moved files for a week, delete them then"). `when` is ISO 8601 with a UTC offset and in the future; `title` is a few words. The owner sees a clock key with the date on your message and presses it once to accept.
- **When he accepts, his reply on the thread says "schedule this".** Then call `task_manager_add` with `fire_at` set to the offered `when` and that title, and reply with the date you scheduled. Do not offer a time you would not file yourself, and offer at most one per reply.
- **A send can now name the thread.** When the owner replied on a task, the send says "the owner replied in the thread of task N (message M)". Read the thread with `task_manager_tasks_list item=N` (or `task_manager_changes`) before you answer.
- **Always pass `task_item` on a crosstalk send about a task (guide rev 100).** `crosstalk_send` takes an optional `task_item` (the Task Manager item id); a `crosstalk_reply` inherits its parent's when you give none. It is how the task is traced across sessions: the item shows a crosstalk trail (who, to whom, when, first line) built from it. Leave it out only when the message is not about a task.

## 31. Waiting: say what and when, the stale timer, checks and the callback (guide rev 73, forks rev 83)

- **A move to `waiting` is refused without `waiting_on`** (what exactly, short) **and `wait_kind`** (`install`, `session`, `person`, `vendor`, `other`). Give `expect_by` (ISO 8601 with a UTC offset) or take the default of the kind: install 1 hour, session 3 hours, person or vendor 24 hours; `other` has no default, so name the time. A wait on the owner is refused: waiting on him is a question, use `task_manager_ask` (an install he runs, such as a handoff script, is fine). The owner's own moves are never refused. A fork cannot set `waiting` (use `parent_waits`, below). Parking a task again counts earlier parks: moving it to `open` and re-parking is the one extension (`extend_reason`), and a third park in two days is refused: ask the owner.
- **A wait that ends at a KNOWN TIME is a schedule, not a wait** (guide rev 116, #2665, the owner, 2026-10-28). If you know the clock time the blocker ends ("the vendor opens at 9", "retry after the 30th"), do not park the task: move it to `todo` with `fire_at` (ISO 8601 with a UTC offset) and Carnivore sends it to you then. A park that says so with `wait_until` (the same kind of time) is refused with code `task_manager_use_fire_at`, and the refusal names the `fire_at` to send. Carnivore never guesses a time from your words, so say it in `wait_until` or `fire_at`; a wait with no fixed time (an install, a person, a check) stays a wait.
- **The stale timer.** When `expect_by` plus half again that long (at least 15 minutes) passes, the task goes back to `open` and you are sent word. The thread says what you named, that it has not cleared, and asks: is it still blocked and on what exactly, and can you do that part yourself? You have three ways out: **clear it** (set `review`, or keep it `open` and work), **extend it once** (`task_manager_update` `state: waiting` again with `extend_reason`, why it is still blocked, and a new `expect_by`; a second extension is refused), or **ask the owner** with `task_manager_ask`. If the extension runs out too, Carnivore asks the owner (push, drop or wait longer) and the task stays waiting until he answers; push sends it back to you with a send, drop parks it in `todo`. The nudge never touches a waiting task; the timer is the only thing that wakes one.
- **A check clears the wait by itself.** Add `wait_check` to the park, one object from a fixed menu (never a command): `{kind: version_live, version}`, `{kind: git_contains, repo, ref, sha}` (repo is this app's repo or one of its worktrees), `{kind: issue_closed | pr_merged, repo: owner/repo, number}`, `{kind: item_state, item, state}` (runs the moment that task changes), `{kind: session_idle, session}`, `{kind: file_exists, path}`, `{kind: url_ok, url}` (loopback, or a host the owner allow-listed). The server runs it with backoff (1 minute doubling to 30). A pass moves the task to `open` and sends you `cleared: <what>`. A check it cannot measure (no auth, no network) reports unknown and never passes.
- **The callback.** The park answer carries `wait_callback.token` ONCE: a one-time secret that works for this wait only and dies when it ends. Give it to a script, a build, another agent or a webhook; it POSTs `{token, result: "cleared" | "failed", reason?}` to `/api/v1/cplugs/huddle/items/<id>/wait/resolve` (the body, never argv or the URL; no other credential needed). `task_manager_wait_update {item, result, reason?}` does the same as an agent. `cleared` and `failed` both return the task to `open` with a line on the thread. Never print the token in a log or a message. A queued handoff script may carry the header line `# carnivore-wait: <item id> <token>`; the handoff runner then calls back when the owner has run it.

- **Waiting on its forks** (guide rev 83). Split a task with `task_manager_fork` `parent_waits: true` and the original moves to `waiting` until none of its forks is `open` or `waiting` (a fork in `review`, `done` or `todo`, or deleted, no longer holds it). Forked first? `task_manager_update` `state: waiting, wait_kind: children` does the same (no `expect_by`, no check, no timer; refused when no fork is still open). Carnivore clears it when the last fork finishes: the task goes to `open`, the thread says `cleared: its forked tasks are done` and you are sent word. To go on without them, `task_manager_wait_update {item, result: cleared, reason}`. The owner's reply clears it too. A task waits on its forks OR on one park, never both: clear one before the other.

## 33. Subtasks, the review lock and blockers (guide rev 109)

- **A subtask is a fork** (`task_manager_fork`; `forked_from` names the parent). `task_manager_tasks_list` `item` of the parent lists them.
- **Your review.** `review` on a parent is refused while a subtask is not in `review` or `done`; the refusal names each (id, title, state). Finish each and set it to `review`, or ask the owner to tick or delete it.
- **His tick.** Refused while a subtask is not `done` (one in `review` still locks it) or a blocker stands; his screen says why. Name the subtasks in `review_description`.
- **Blockers.** A task waiting on its forks (section 31) is held: your moves stay `waiting`, `blocked` names the forks, his tick is refused. It clears when they finish, or with `task_manager_wait_update {item, result: cleared, reason}`. A park never blocks review.
- **Review checks are not a lock**: he is warned, not stopped. Tasks already past these rules stay as they are; only the next move is checked.
